# Threat-source and detection research, 2026-11-23

Scope: what a read-only, local-first Windows security product can add from public sources, and what it must not claim.
Every candidate below was probed from this machine on 2026-11-23 with a plain HTTPS GET (no credentials, no redirect
following beyond the probe). Counts and states are what the endpoints returned that day, not marketing figures.

## Added in this cycle

| Source | Endpoint | Observed | Licence | Why it is worth a slot |
|---|---|---|---|---|
| Spamhaus ASN-DROP | `https://www.spamhaus.org/drop/asndrop.json` | HTTP 200, 41,032 bytes, NDJSON (`asn`, `rir`, `domain`, `cc`, `asname`) | Spamhaus DROP terms (free use) | The first source in the catalog that is keyed by **network owner** instead of address or name. It can describe a connection whose address is on no indicator list, which is exactly the bulletproof-hosting case that address lists miss. |
| OffSeq Mirage (7-day) | `https://feeds.offseq.com/mirage-feed/latest/ipv4-7d.txt` | HTTP 200, 23,030 bytes, one IPv4 per line (471 addresses in the public 7-day list, from 4,802 seen in 24 hours) | CC BY 4.0, TLP:CLEAR | Independently operated honeypot telemetry with an explicit redistribution licence and stable paths. Honeypot observation is a different kind of evidence from blocklist aggregation. |

Both were chosen because they add a **kind** of evidence the catalog lacked (network ownership; first-party honeypot
observation), not because they raise a count. The ASN list is attached to every established connection as a network
property and explicitly never as a program verdict; the honeypot list enters the ordinary IP-reputation path.

## Retired after this probe

`threatview-md5` (`https://threatview.io/Downloads/MD5-HASH-ALL.txt`) answered HTTP 200 with **0 bytes**. An empty 200
cannot be distinguished from a truncated download, and the strict parser already refuses it, so the source could only ever
show as failed. It is now retired with that reason instead of staying active. The provider's SHA-1/SHA-256 feed (492 bytes
that day), Mandiant and DigitalSide still supply hash evidence, and the active catalog is 59 sources.

## Dark-web and criminal-market data

No Tor, paste site, Telegram channel, ransomware leak site or criminal market was accessed, and none should be.
Three separate reasons, in order of importance:

1. **Legality and safety.** Scraped criminal-market data is often obtained unlawfully and can contain personal data of
   victims. Buying or ingesting it is not a defensive capability.
2. **Provenance.** A stolen-log or initial-access listing cannot be verified, dated or licensed, so it cannot satisfy
   the catalog's rules (fixed HTTPS endpoint, stated licence, publication timestamp, strict parser, size bound).
3. **The product's own contract.** Downpour never sends anything about the PC to a source and never contacts a hostile
   host. Both would be required to enrich from those sources.

What *is* legitimate and commercial exists (breach and stealer-log intelligence from established vendors), and it needs a
paid contract, an API key in the credential store, and a documented per-query privacy statement. That is a product
decision for the owner, not something to wire silently.

## Detection capability gaps worth more than another list

- **Newly observed domains.** The single largest gap: the DNS route scores DGA-likeness but has no "first seen today"
  signal. It is the classic phishing and loader tell. Blocked on the SANS licence above; a licensed alternative or a
  certificate-transparency feed with clear terms would close it.
- **ETW providers.** The catalog's Windows-event coverage is allow-listed event IDs plus fixed subscriptions. Microsoft's
  own guidance treats Sysmon events as behavioural *chains* (process create → DNS query → network connect → file create →
  registry write), and MITRE CTID's 2026 Windows case study found that only 26 of 84 ATT&CK techniques tagged in a rule
  set had implementation-level coverage. Chasing ATT&CK tag counts would be dishonest; sequencing the events already
  collected is the cheaper, more real improvement.
- **AMSI content.** AMSI exists for script and buffer scanning, but content is deliberately not persisted. The honest
  ceiling here is a verdict and a bounded excerpt, which needs a consent design before it can grow.
- **Egress volume.** Per-connection byte counts are absent from `GetExtendedTcpTable`; ETW or an elevated ESTATS query is
  required. Baselining volume without that would be guesswork.
- **Signed release and install integrity.** Already built (`ReleaseTrustPolicy`, `InstallationIntegrity`) but the release
  key remains offline custody, which no amount of web research changes.

## Rules this research keeps

- A source is added only with a fixed HTTPS endpoint, a stated licence, a size bound, a strict parser and a failure state.
- Listing count is never confidence: aggregators repeat upstream data, which is why the verdict engine says independence
  is not established.
- Network ownership is context. A connection to a Spamhaus-listed ASN is a fact about routing, not proof that the program
  is malicious, and the wording says so in every surface that shows it.
