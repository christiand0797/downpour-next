# Security policy and development requirements

Downpour Next is security-sensitive software. The repository is public and does not yet have a formal response SLA. Report vulnerabilities privately to the repository owner; do not publish exploit details before a fix is available.

## Secure defaults

- Desktop runs as the signed-in user. The service uses the narrowest service identity and privileges required by each sensor.
- Observation, detection, recommendation, and response are separate stages. System-changing actions default off.
- IPC uses local named pipes, versioned bounded contracts, ACLs, and explicit timeouts. Never expose an unauthenticated network listener for local UI communication.
- No arbitrary shell, PowerShell, command-line, URL, path, or registry payload reaches the service. Use typed allow-listed operations only.
- Secrets use Windows-protected storage. Minimize or avoid personal data, command lines, clipboard content, file contents, browser data, and remote data transfer.
- Feed and rule inputs are untrusted. Require TLS, size/time limits, parser hardening, signature/integrity verification where available, and provenance metadata.
- Quarantine and evidence require integrity manifests, access control, bounded storage, collision handling, verified restore, and recovery procedures.
- Actions require policy authorization, operator preview where appropriate, audit records, bounded execution, a safe failure path, and tested rollback where possible.
- Dependencies and GitHub Actions are supply-chain inputs. Pin versions, review updates, keep secrets out of CI, and generate an SBOM before release.

## User-approved data handling (2026-10-07)

The repository owner made these decisions explicitly. Keep the stated limits when implementing or changing them.

- **PowerShell script-block text (Event 4104 `ScriptBlockText`) for Sigma and AMSI: approved, on by default, with a Settings switch to turn it off.** The text is analyzed in the service's memory only. It must never be persisted, logged, exported, sent over IPC to the desktop, or included in alerts. Alerts carry only the rule name, severity, technique, and event record ID. Analyzed text is bounded in size. (WORK_QUEUE DN-029)
- **Automatic threat-intelligence lookups for alert indicators: approved.** Indicators (public IP addresses, file hashes, domains) taken from alerts may be sent automatically to services you configure with your own API keys. Keys are stored with DPAPI for the current user and are never logged or exported. Private, loopback, and link-local addresses are never sent. Lookups are rate-limited and cached, every outbound lookup is recorded locally (service, indicator type, time), and a master switch turns lookups off. (DN-025)
- **YARA: approved (2026-10-07)** per `docs/YARA_EVALUATION.md`: YARA-X C API with our own binding, DLL built in CI from a pinned release and hash-verified, scanning in an isolated helper process. (DN-026)
- **Response actions: approved to build and enable (2026-10-07)** per `docs/ACTION_BROKER_THREAT_MODEL.md`, one phase at a time. Each phase is switched on only after its denial, crash, rollback, and audit tests pass. Every action still requires an itemized, per-request confirmation; there is no automatic remediation. Host isolation and lockdown must expire automatically. Until release signing exists (DN-010), the desktop caller is verified by image path and process identity, which is weaker than signature verification; this limitation is stated in the UI. (DN-008)
- **Ransomware document sampling: approved, on by default, with a Settings switch.** The Ransomware screen may read up to 64 KB of documents in protected folders to compute an entropy score. Only the score is kept.
- **Anti-Stalker (owner request 2026-10-07):** reads Windows camera/microphone/screen-capture/location usage records, remote session metadata (client name/address), process names and installed-software names, and keeps a local watch log (`state/watch-log.v1.jsonl`, 2 MiB rollover). Nothing leaves the PC. (DN-030)
- **Threat databases (owner request 2026-10-07):** on by default with a Settings switch. Downloads only catalogued public feeds in full from fixed HTTPS hosts (no redirects, size limits, strict parsers, integrity-checked cache); no indicator, address or file from this PC is ever sent. Locally hashes loaded drivers and running programs outside the Windows folder (128 MiB cap each) and reads the TCP table with owning process IDs and the DNS cache. IP origin is an offline country/network lookup that never identifies a person; there is no active tracking or "hack back". Matches become findings; nothing is blocked automatically. (DN-031)

## Current threat model

Assets include host telemetry, user settings, alert/evidence history, threat-feed state, rules/models, and any future quarantine contents. Threats include malicious local processes/users, malformed or spoofed IPC payloads, parser exploits, untrusted feeds/rules/files, dependency or update compromise, privilege escalation, denial of service, data disclosure, and unsafe automated remediation.

The portable application currently runs the desktop and bundled sensor service as the signed-in user. Telemetry pipes are bounded and ACL-restricted to that user and LocalSystem. Separate quarantine, process termination, firewall, and USB action pipes implement fixed operations, parent-desktop image/process checks, one-use expiring consent, feature settings, and audit records. These four phases are enabled per the owner's recorded decision; they do not run automatic remediation. The draft host-isolation phase is not release-ready: recovery must survive service shutdown, partial firewall changes must roll back, and release must remain available without the pipe. See `docs/AGENT_COORDINATION.md`.

The application remains unsigned. Parent/process/path checks are weaker than publisher signature verification, same-user state is not resistant to same-user malware, and independent named-pipe server identity verification remains unfinished. The portable app is an early development product, not an audited security product. Installing under a separate service identity requires a dedicated service/client SID ACL and consent/elevation design. Never broaden pipes to Authenticated Users or Everyone to bypass access failures. The action audit log is hash-chained with HMAC-SHA256 under a DPAPI-protected per-user key and anchored against truncation; a break raises a CRITICAL integrity finding. It does not withstand malware already running as the same user, which can use the same key. Audio Shield (`Downpour.Audio.v1`) is read-only: it uses Core Audio session and meter interfaces (levels only, never a capture stream or audio content), registry reads, and signature checks; its fixes reuse the existing quarantine and process-termination brokers or open fixed ms-settings pages. Protected logs (Security, Sysmon) are read only when the signed-in account may read them; Downpour does not elevate to get them and never changes group membership. It shows the person a copyable, locale-independent command (Add-LocalGroupMember -SID S-1-5-32-573) to run themselves in an administrator terminal, which grants read-only event log access. AMSI scan errors must remain explicitly unavailable, and metadata-only Sysmon events must not be described as confirmed malware.

## Before enabling a security feature

Record its data classification, trust boundary, least-privilege needs, privacy impact, failure behavior, test evidence, audit fields, and rollback plan in the feature documentation and queue. Run negative tests for access denial, malformed input, resource exhaustion, timeout, stale state, and recovery. Do not mark it implemented until the evidence is recorded.

## Elevated fixer (Downpour.Fixer)

`Downpour.Fixer.exe` is the only component that runs as administrator. It is started by the desktop with Windows' consent prompt for each run and accepts exactly three validated commands (`apply` catalog fix IDs, `undo` a backup ID, `updates software|drivers|all`); everything else is refused before any change. Fixes are a fixed catalog (`HardeningFixes`) of HKLM values, local account disable, firewall profiles and Defender preferences; previous values are backed up (a deleted auto-logon password is never stored), a partly failed fix is rolled back, and undo only restores backups the fixer wrote. Results, backups and a SHA-256-chained audit log live in `%ProgramData%\DownpourNext\fixer`, owned by Administrators with users read-only; a pre-existing folder that is a link or not administrator-owned is refused. Windows updates and drivers come only from the Windows Update Agent (Microsoft-signed, applicable to this hardware); updates needing interactive input are skipped and the PC is never restarted automatically. Known limit: the portable folder is user-writable, so same-user malware could replace the fixer before the person approves the prompt (the prompt shows an unknown publisher either way); code signing and an installed location fix this.
